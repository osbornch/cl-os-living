先澄清一点:我从没说 AI Infra 是个轻松就能学好、做好的东西。待在技术最前沿,意味着你要不断消化新知识。比如新的优化策略、新的模型架构、各种 paper 和 report。所以这条路径更适合有自己想法、内驱力强的人。人各有志,如果你更看重个人生活和休闲时光,我并不建议你踏进这样一个行业。

下面先是我的时间线,后面我会把这几个月摸索出来的方法单独讲清楚。

去年 10 月|onboard 基础。 我开始系统学 LLM 相关知识,加上之前在学校上过一点 machine learning,基本概念和原理上手得比较快。这一步没有捷径,但也没那么可怕，有 CS 底子的人,补齐概念比你想象的快。

10 月—次年 3 月|夯实基础 + 读源码。 这几个月我一直在看各种 LLM 的优化策略和原理,想把地基打牢。同时开始读 inference framework 的代码,比如 SGLang。也是在这期间,我给 SGLang 做了一两期 tutorial 视频,借此认识了一些开源社区的成员。

3 月起|进组,开始真正贡献。 我加入了 SGLang 最新的项目 SGLang-Omni。从那时到现在,我一直在给 SGLang-Omni 提交代码、做一些优化,也攒下了自己的技术积累和感悟,陆续写成了博客。

时间线讲完了。接下来我也想分享几点关于我总结出来的方法论：

一、怎么读一个庞大的开源代码库
先读"结构"而不是"细节"。 第一遍的目标不是看懂每个函数,而是搞清楚这个 repo 分几大块、每块负责什么、一个请求进来大概会流经哪些模块。把目录结构、核心模块的边界摸清楚/

用"一条请求的生命周期"当主线去穿。 与其漫无目的地翻,不如挑一个具体问题——比如"一个推理请求从进来到吐出结果,中间经过了什么"——然后顺着这条线去追代码。这样你读到的每一段都有上下文,不会迷路。

看懂 20% 的核心路径,比看完 100% 更有用。 任何大项目里,真正高频、真正关键的代码就那一小部分。先吃透主干,分支和边角等你真要动它的时候再看。

二、怎么找到并完成提交好的PR
这是被问最多的问题,也是最多人卡住的地方。我的经验是,提交PR，或者说尤其第一个 PR 不该是"憋个大招",而是尝试完成一次完整的贡献流程:

首先，所有的PR贡献一定是基于第一点，你已经有了对系统的理解了，在开始贡献，希望大家对自己的PR都有责任心，不要随便vibe一个。

从小处切入,别一上来啃硬骨头。 文档里的错漏、一个不清晰的报错信息、一个缺失的测试、issue 里标着 good first issue 的任务等等，这些都是极好的起点。第一个 PR 的价值不在于难度,而在于让你走通"fork → 改 → 提 PR → 过 CI → review → merge"这一整套流程,把陌生感消掉。

去 issue 区和社区频道里"蹲"。 很多贡献机会不是你凭空找的,是别人已经提出来、还没人做的。多看 issue、多看 讨论，说不定就能找到还没人做的活儿。

根据直觉找问题 很多时候我们发现在开源社区的开发中，有一些数据，比如benchmark结果，或者其他的一些设计，并不符合直觉。这往往伴随着一些bug的发现和优化可能性。这是一个非常值得关注的点，当你有了对系统的理解之后，自然而然就会产生一些直觉，然后带着这些直觉，就会有疑问。比如“这个模型为什么比另外一个模型快”，“为什么这个优化策略在A模型效果好，在B模型上效果不好”，等等。这些问题就可以自己尝试profile实验，然后探索出结果。往往这些问题发现了之后，都能产生优质的PR优化。这也是我们开源社区非常鼓励大家做的事情。

三、怎么在一个飞速变化的领域里持续学
接受"没有成功路径"这件事。 LLM 这块,大家都是摸着石头过河。这是一个太新的领域,几乎颠覆了过去十年的经验积累。所以不要等一门"完整课程"把你教会。因为这样的课程还不存在,能带你上路的是 paper、release note、别人的博客,和源码本身。

用输出倒逼输入。 写博客、做 tutorial、给别人讲，这类型的输出是我验证过最高效的学法。你以为你懂了,一旦要讲给别人听,漏洞立刻暴露。我的很多技术积累,都是在"要写出来"的压力下才真正夯实的。

找到社区,和人一起进步。 有意思的是,这个社区里几乎全是年轻人,有想法、有拼劲,热情极高。一个人闷头学很容易卡死,而在社区里,你的问题常常几句话就有人解答,你的进步也会快得多。

回头看,最大的一个感悟是:这条路没有标准答案,但每一步都有方法。 想开始学习,最好的时代是两年前,第二好的时代,就是现在。
