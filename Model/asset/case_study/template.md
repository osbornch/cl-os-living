# Software Asset 分析框架

## 核心问题

研究软件 Asset 时，不要先问：

> 我能做什么软件？

而要问：

> 什么样的软件，能够把一次性的工程劳动，沉淀成可重复交付、持续增值、低边际成本的资产？

---

# 一、先判断：它为什么是 Asset？

普通软件项目和软件资产的区别，不在于有没有代码，而在于它能否脱离单次劳动，持续产生价值。

## 六个判断标准

| 维度    | 核心问题                      |
| ----- | ------------------------- |
| 可重复使用 | 同一套能力能否服务多个用户、场景或项目？      |
| 低边际成本 | 增加一个用户，成本是否远低于重新做一遍？      |
| 可积累   | 数据、模型、工作流、品牌和用户关系是否越用越强？  |
| 可分发   | 能否通过互联网、API、插件或平台低成本触达用户？ |
| 可收费   | 是否存在清晰的价值交换和付费主体？         |
| 可脱离本人 | 不需要创始人或开发者每次亲自参与，也能交付结果吗？ |

可以简单理解为：

> **软件 Asset = 可复用能力 × 可分发性 × 可持续价值 × 所有权**

如果一个软件每次都需要大量定制、解释和人工服务，它更接近“软件化服务”，而不是成熟的软件资产。

# 二、软件 Asset 八层分析框架

## 1. Problem：它解决什么问题？

不要从功能开始，要从问题开始。

### 分析问题

* 谁反复遇到这个问题？
* 问题发生频率有多高？
* 不解决的成本是什么？
* 用户目前如何替代解决？
* 这是“有点烦”，还是“必须解决”？
* 这个问题未来会变得更严重还是更轻？

### 优先关注四类问题

1. **高频问题**

   * 每天或每周发生

2. **高损失问题**

   * 一旦发生，损失很大

3. **高人力问题**

   * 当前依赖大量人工完成

4. **高认知问题**

   * 用户不知道如何判断、分析或决策

例如，Incident Response 同时具有：

* 高损失
* 高人力
* 高认知负担
* 一定的重复频率

---

## 2. User：谁拥有问题，谁为它付钱？

至少区分四类角色。

| 角色          | 核心问题        |
| ----------- | ----------- |
| User        | 谁实际使用产品？    |
| Buyer       | 谁决定购买并支付费用？ |
| Beneficiary | 谁最终从产品中受益？  |
| Blocker     | 谁可能阻止产品被采用？ |

### 示例：Incident Intelligence 产品

* **User**：On-call Engineer
* **Buyer**：Engineering Director、VP Engineering
* **Beneficiary**：研发组织和客户
* **Blocker**：Security、Compliance、Platform Team

很多软件失败，不是因为没有用户价值，而是因为没有找到明确的购买者和预算来源。

---

## 3. Value：它创造什么可衡量价值？

软件价值通常来自五个方向。

### 1. 节省时间

例如：

> 将两小时的事故调查缩短到十分钟。

### 2. 降低成本

例如：

* 减少人工操作
* 减少云资源浪费
* 减少第三方工具费用
* 降低客户支持成本

### 3. 增加收入

例如：

* 提高转化率
* 提高成交率
* 提高留存率
* 提高客单价

### 4. 降低风险

例如：

* 减少生产事故
* 降低合规风险
* 减少错误决策
* 避免数据泄漏

### 5. 提升能力上限

例如：

* 让非专家完成原本只有专家能完成的工作
* 让一个专家同时管理更多任务
* 让组织拥有过去不具备的能力

### 价值表达模板

> 对于【某类用户】，该软件通过【核心机制】，把【旧指标】从 X 改善到 Y。

### 示例

> 对于负责大型分布式系统的 On-call 团队，该软件通过自动聚合日志、变更和历史事故，将初步定位时间从 45 分钟降低到 10 分钟。

---

## 4. Asset Core：真正沉淀下来的是什么？

软件 Asset 不只是代码。

真正能够积累的资产，通常包括以下六类。

| Asset 类型           | 示例               |
| ------------------ | ---------------- |
| Code Asset         | 引擎、SDK、框架、算法     |
| Data Asset         | 标注数据、历史行为、行业数据库  |
| Workflow Asset     | 被验证过的流程、模板、自动化链路 |
| Intelligence Asset | 模型、规则、推荐和决策系统    |
| Distribution Asset | 用户、渠道、插件生态、社区    |
| Trust Asset        | 品牌、安全认证、行业信誉     |

### 核心问题

> 即使竞争者复制了界面和功能，什么东西仍然很难复制？

优秀的软件资产通常不只有一层。

### 常见演化路径

* **初期**：代码与工作流
* **中期**：用户行为与业务数据
* **后期**：生态、品牌、网络效应与行业标准

---

## 5. Engine：价值如何被持续生产？

画出软件的价值生产链路。

```text
用户输入
→ 软件处理
→ 产生结果
→ 用户采取行动
→ 生成新数据
→ 产品能力增强
→ 吸引更多用户
```

### 示例：Incident 产品

```text
接入系统
→ 收集事故和变更数据
→ 给出关联分析
→ 工程师确认根因
→ 沉淀事故知识
→ 下一次推荐更准确
→ 团队更加依赖系统
```

### 核心判断

> 每一次使用，是否都在增强资产本身？

如果用户越多，只带来更多服务器和支持成本，却没有产生数据、品牌、网络、流程或知识积累，那么资产飞轮较弱。

---

## 6. Economics：经济模型是否成立？

## 收入分析

* 一次性付费还是订阅？
* 按用户、按团队、按用量还是按结果收费？
* 用户愿意为哪个指标付费？
* 客单价上限由什么决定？
* 收入是否具有持续性和可预测性？

## 成本分析

* 产品开发成本
* 云计算成本
* 模型训练与推理成本
* 获客成本
* 客户支持成本
* 集成和实施成本
* 安全与合规成本

## 核心问题

* 新增一个客户需要多少额外劳动？
* 客户使用越多，毛利提高还是降低？
* 是否能形成经常性收入？
* 客户为什么会续费？
* 客户流失后，哪些投入无法回收？
* 是否存在高昂的人工交付成本？

### 优秀软件资产的典型经济特征

> 高前期建设成本
>
> * 低复制成本
> * 经常性收入
> * 较高切换成本

---

## 7. Moat：护城河从哪里形成？

软件功能本身通常不是长期护城河。

可以检查以下七种护城河。

### 1. 数据护城河

拥有竞争者无法轻易获得的数据。

### 2. 工作流嵌入

产品成为用户日常流程的一部分。

### 3. 切换成本

迁移数据、规则、集成和团队习惯非常困难。

### 4. 网络效应

用户越多，其他用户获得的价值越大。

### 5. 生态系统

拥有插件、开发者、合作伙伴和第三方集成。

### 6. 品牌与信任

尤其适用于：

* 医疗
* 金融
* 安全
* 企业基础设施

### 7. 执行复利

团队持续迭代速度远高于竞争者。

### 不要只问

> 别人能不能复制？

更应该问：

> 即使别人复制了第一版，为什么三年后我仍然会更强？

---

## 8. Owner Fit：为什么是你来做？

这一层分析创始人或建设者与资产的匹配度。

### 分析问题

* 你是否深刻理解这个问题？
* 你是否能够接触真实用户？
* 你是否拥有独特的技术能力？
* 你是否能低成本做出第一版？
* 你是否拥有可信的分发渠道？
* 你是否愿意研究这个领域五年以上？
* 这个资产是否强化你想成为的身份？
* 你的经历是否让你看见别人看不见的问题？

你的优势可能不只是会写代码，而是能够理解：

* 可靠性工程
* 数据平台
* Agent 系统
* 复杂组织工作流
* 模糊问题的结构化
* 从事故中提炼知识和系统

因此，适合你的软件资产方向可能包括：

* 工程决策系统
* Incident Intelligence
* Agent Observability
* Agent Evaluation
* 企业知识资产化
* AI 工作流平台
* AI 基础设施中的高认知、高信任工具

# 三、软件资产的四个发展阶段

## 阶段一：Tool

解决一个具体任务。

### 示例

* 日志分析脚本
* PR Review 工具
* Incident Timeline Generator
* 数据迁移检查器

### 需要证明

> 功能确实有用。

---

## 阶段二：Product

多人可以稳定使用，并且拥有明确的：

* 用户体验
* 交付方式
* 付费方式
* 支持体系

### 需要证明

> 有人会持续使用并愿意付费。

---

## 阶段三：Platform

其他产品、开发者或工作流开始建立在它之上。

### 特征

* 提供 API
* 提供插件系统
* 提供 SDK
* 支持第三方扩展
* 承载多个使用场景

### 需要证明

> 别人开始依赖它创造价值。

---

## 阶段四：Infrastructure / Ecosystem

成为某个领域默认的一层，形成：

* 数据积累
* 行业标准
* 开发者生态
* 品牌信任
* 网络效应

### 需要证明

> 它不再只是一个产品，而是行业基础设施。

# 六、今天的研究建议

## 推荐案例一：Datadog

重点研究：

* 如何从 Monitoring Tool 发展成多产品平台
* Logs、Metrics、Traces 如何互相增强
* 为什么客户会不断增加产品使用
* 数据和工作流如何形成切换成本
* 它的扩张收入模型如何成立

---

## 推荐案例二：GitHub

重点研究：

* 代码仓库如何成为协作基础设施
* 用户身份和开源社区如何形成网络效应
* Actions、Marketplace 和 API 如何形成平台
* Copilot 如何建立在原有分发和工作流之上
* 为什么 GitHub 不只是代码存储工具

---

## 推荐案例三：Cursor

重点研究：

* 高频开发工作流如何形成使用习惯
* 产品价值来自模型还是交互体验
* Codebase Context 是否能够成为资产
* 它如何与基础模型公司区分
* 它是否能够从工具发展成平台
* 它真正的长期护城河是什么

---

# 七、60—90 分钟研究流程

## 第一步：理解产品

时间：15 分钟

* 它解决什么问题？

* 核心功能是什么？

时间：20 分钟

* 真正沉淀下来的是什么？

* 哪部分最难复制？

时间：15 分钟

回答：

* 谁付费？

* 新增客户是否需要大量人工？

---

# 核心认知

研究软件 Asset 的目的，不是马上找到一个创业点子。

真正要训练的是一种能力：

> 从看见软件功能，升级到看见功能背后的价值生产系统、积累机制和所有权结构。

最终要能够回答：

> 这个软件究竟在持续积累什么？

> 为什么它明年会比今年更有价值？

> 为什么一次工程劳动，可以转化为长期、重复、可扩张的价值？
